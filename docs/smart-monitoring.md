# Disk SMART monitoring: Proxmox hosts and TrueNAS

This runbook covers getting disk SMART data from the 4 Proxmox hosts and the TrueNAS box into
Prometheus. Each host runs the prometheus-community
[smartctl_exporter](https://github.com/prometheus-community/smartctl_exporter) on `:9633`, and
Prometheus scrapes it with the `smartctl` job.

> **The host side is not in git.** The PVE hosts are not in the Ansible inventory, and TrueNAS
> apps are configured in its own UI. Everything under "Install" below is done by hand, once per
> host. The repo only holds the scrape job, the alerts and the dashboard.

## Why

A disk can log uncorrectable reads and remap sectors for weeks while its SMART overall-health
still says **PASSED**. That verdict only flips when a *normalized* attribute value falls to its
threshold, which is long after the *raw* error counts have started to climb. Ceph or ZFS
redundancy hides the damage in the meantime. So the alerts here watch raw counters going **up**,
and treat PASSED/FAILED as the late signal.

## What runs where

| | |
|---|---|
| PVE hosts (pve-m900, pve-r630-01/02/03) | Debian package `prometheus-smartctl-exporter` from **trixie-backports**, systemd unit `smartctl_exporter.service`, runs as root |
| TrueNAS | Custom App `smartctl-exporter`, image `prometheuscommunity/smartctl-exporter:v0.15.0`, privileged, root |
| Scrape job | `smartctl` in `kubernetes/apps/monitoring/kube-prometheus-stack/helmrelease.yaml`, 60s interval, `instance`/`host` = host name |
| Alerts | `kubernetes/apps/monitoring/kube-prometheus-stack/prometheusrule-smart.yaml` |
| Dashboard | **Disks / SMART**, generated by `scripts/monitoring/gen_smart_dashboard.py` into `kubernetes/apps/monitoring/smart/dashboard.yaml` |

The PVE hosts run 0.14.0 (the version in trixie-backports) and TrueNAS runs 0.15.0. Both export
the same metric names and the same `device` label (`sda`, `nvme0`). The only difference that
matters here is that 0.15.0 adds a SAS endurance metric, which the dashboard uses when present.

## Install

Do this **before** merging the PR if you can. Once the scrape job is live, every host without an
exporter fires `SmartctlExporterDown` after 15 minutes.

### Proxmox hosts (all 4)

The package is **not** in trixie main, only in trixie-backports. PVE 9 already ships
`smartmontools`, which is all the package depends on.

1. Enable trixie-backports. Skip this if `apt policy` already lists a `trixie-backports` origin.

   ```sh
   cat > /etc/apt/sources.list.d/debian-backports.sources <<'EOF'
   Types: deb
   URIs: http://deb.debian.org/debian
   Suites: trixie-backports
   Components: main
   Signed-By: /usr/share/keyrings/debian-archive-keyring.gpg
   EOF
   apt update
   ```

   Backports are never installed unless asked for by name (`-t trixie-backports`). Once a package
   is installed from there, `apt upgrade` keeps it current from backports as well.

2. Install and start it:

   ```sh
   apt policy prometheus-smartctl-exporter   # expect a 0.14.0-2~bpo13+1 candidate
   apt install -t trixie-backports prometheus-smartctl-exporter
   systemctl enable --now smartctl_exporter
   ```

   The unit runs `/usr/bin/smartctl_exporter` with no flags. The defaults are the right ones:
   listen on `:9633`, find disks with `smartctl --scan` and rescan every 10m, re-read each disk at
   most every 60s, and skip disks in standby rather than spinning them up.

3. Verify:

   ```sh
   systemctl status smartctl_exporter --no-pager
   curl -s localhost:9633/metrics | grep smartctl_device_attribute | head
   curl -s localhost:9633/metrics | grep -E '^smartctl_devices |^smartctl_device_smart_status'
   smartctl --scan
   ```

   `smartctl_devices` should equal the number of lines from `smartctl --scan`, and every disk
   should have a `smartctl_device_smart_status` line. On pve-m900, if it has an NVMe drive, also
   check `curl -s localhost:9633/metrics | grep smartctl_device_media_errors`.

   If a disk is missing, run `smartctl -x /dev/<disk>` by hand. The R630s' SATA SSDs answer plain
   `smartctl` with no `-d` option. A disk behind a RAID controller (not HBA mode) would need a
   `--smartctl.device=/dev/sdX;megaraid,N` flag added with `systemctl edit smartctl_exporter`.

4. If the PVE firewall is on, allow TCP 9633 in from the same source the `ceph` scrape on :9283
   already comes from. The endpoint is read-only and has no auth, the same as ceph-mgr's.

### TrueNAS

Apps → Discover Apps → ⋮ → **Install via YAML**, name `smartctl-exporter`:

```yaml
services:
  smartctl-exporter:
    image: prometheuscommunity/smartctl-exporter:v0.15.0
    restart: unless-stopped
    privileged: true
    user: root
    ports:
      - "9633:9633"
```

- **`privileged: true` and `user: root` are both required.** Privileged gives the container the
  host's disk device nodes. Root is needed on top of that because the image defaults to `nobody`,
  and the kernel blocks the SMART passthrough ioctls for non-root users even with device access
  (upstream README, "Why is root required?"). This is the setup upstream documents for Docker.
- Device nodes are copied in when the container starts. **After adding or replacing a disk,
  restart the app**, or the new disk never shows up.
- The tag is pinned on purpose. It lives on TrueNAS, not in git, so Renovate cannot bump it. Bump
  it by hand and check the upstream CHANGELOG for metric renames first.
- TrueNAS's own SMART tests and `smartd` are unaffected, because the exporter only reads. If HDD
  standby is ever turned on for the pool disks, the exporter skips sleeping disks and
  `SmartctlDisksUnreadable` fires for them.

Verify from a TrueNAS shell. The output should match the PVE checks above:

```sh
curl -s localhost:9633/metrics | grep -E '^smartctl_devices |^smartctl_device_smart_status'
smartctl --scan
```

A textfile-collector script on the existing node_exporter app was the fallback. It wasn't needed,
because the container sees the HBA-attached disks the same way the host does and uses the same
metric schema as the PVE hosts.

## After merge

```sh
# all 5 targets up
kubectl get --raw '/api/v1/namespaces/monitoring/services/kube-prometheus-stack-prometheus:9090/proxy/api/v1/query?query=up%7Bjob%3D%22smartctl%22%7D'
```

Then open **Disks / SMART** in Grafana. Every disk should have a row with SMART = PASSED, a
temperature and power-on time. SSDs should also show a wear figure.

## Alerts

| Alert | Severity | Fires when |
|---|---|---|
| `SmartDiskErrorsIncreased` | warning | Any error counter is above its 24h low |
| `SmartDiskErrorsGrowing` | critical | The same, and it rose in 3+ steps or by 10+ within 24h |
| `SmartDiskFailed` | critical | The disk's own overall-health verdict is FAILED |
| `SmartctlExporterDown` | warning | A target can't be scraped for 15m |
| `SmartctlDisksUnreadable` | warning | The exporter is up but found no disks, or has no data for some of them, for 30m |
| `SmartDiskDisappeared` | warning | A disk that reported in the last 24h is gone while its exporter is up |

The counters are raw ATA 5 (reallocated), 183 (runtime bad block), 187 (uncorrectable), 197
(pending), 198 (offline uncorrectable), plus NVMe media errors and SAS grown defects /
uncorrected reads and writes. All of them are collected into one recording rule,
`smartctl:device_error_count`, with a `counter` label.

Things to know when one fires:

- **Counts that were already non-zero don't alert.** Only a rise does. The dashboard's
  "Disks with any errors" stat and the table show the standing counts.
- **A disk swap fires `SmartDiskDisappeared`.** It resolves 24h after the old disk left.
- **Disk names can move.** The recording rule carries the serial, so a `device` name that now
  points at a different disk starts a new series and is not read as a jump.
- **A disk that is still present but can no longer be read stays invisible here.** The exporter
  keeps serving that disk's last good read, so its numbers freeze. Ceph (`CephOSDDown`,
  `CephHealthError`) and ZFS pool state cover that case.
